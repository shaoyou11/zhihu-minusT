# Android 真机基线（2026-08-30）

## 环境

- 设备：vivo V2509A
- 系统：Android 16（API 36）
- 构建：Expo Debug Dev Client，Hermes，新架构
- 连接：USB，`tcp:8081` 通过 ADB reverse 连接 Metro

这些结果用于定位瓶颈，不代表 Release 包的最终性能。

## 首页基线

- Android 冷启动到 Dev Launcher Activity：538 ms；该指标不包含 JS 数据加载完成时间。
- 推荐流请求约 3.0 s 后返回。
- 首页稳定后：580,610 KB PSS、775,754 KB RSS、1,010 个 View、2 个 Activity、0 个 WebView。

Debug Dev Client 自身占用很重，因此后续必须补一轮 Release 对照。

## 优化前：从推荐流打开回答

以回答 `2076226177182835844` 为例：

1. 点击后约 204 ms，详情页再次请求目标 `/answers/:id`。
2. 目标回答请求耗时约 702 ms，在点击后约 906 ms 返回。
3. 问题回答 ID 列表请求耗时约 681 ms。
4. Pager 随后请求了 4 个相邻回答，并查询收藏状态；相关请求持续到点击后约 3.2 s。
5. 详情稳定后达到 656,384 KB PSS 和 1,721 个 View，较首页增加约 75.8 MB PSS 和 711 个 View。

该时间线证明推荐流已经持有正文，但详情查询缓存没有复用它；同时相邻 Pager 页面会继续制造正文请求和挂载压力。

## 优化：复用推荐流回答详情

推荐响应解析后，将满足以下条件的回答写入 React Query 的 `['answer-detail', id]` 缓存：

- 正文是非空 HTML 字符串；
- 包含作者和问题信息；
- 不是付费回答；
- 没有正文截断标记。

已有的更完整详情缓存不会被推荐流覆盖。不满足条件的卡片继续使用原详情接口。

## 优化后真机验证

以回答 `2008568044180480306` 为例，目标 `/answers/:id` 请求已消失。仍然保留：

- 浏览历史写入；
- 当前回答收藏状态；
- 问题下回答 ID 列表，用于 Pager；
- 相邻回答预取，因为推荐流并不包含那些回答。

推荐流缓存与详情页使用相同的 React Query key，已有的目标正文不再经过第二套预览或详情缓存。

## 长按预览复用

`FeedCardPreview` 现在同样使用回答、文章、想法和问题详情页各自的标准 query key。列表项已经带有非空正文时，预览直接使用该正文并禁用详情请求；列表未提供正文时仍按原逻辑请求详情。

自动化 ADB 长按容易被 `Pressable` 识别为普通点击或滚动，因此没有把该手势的截图作为性能证据。请求策略由纯函数回归测试覆盖，真机上普通进入详情的同 key 缓存命中已得到网络日志验证。

## Pager 相邻回答预取

回答 ID 列表返回后，页面在 JS 空闲期预取当前回答左右各一条，最长等待 1.5 s。未聚焦的 Pager 子页只保留空容器，不会因为预取完成就提前挂载完整标题、作者区和富文本 View；真正横滑到该页后才挂载页面，并直接读取已预取的 query 数据。

以回答 `2071904265115792627` 为例：

1. 从推荐流打开时没有目标 `/answers/:id` 请求。
2. 收藏状态、浏览历史和 `include=data[*].id` 的问题回答列表请求正常保留。
3. 回答列表返回后，空闲期预取相邻回答 `3403051004`。
4. 横滑到 `3403051004` 时没有再次请求 `/answers/3403051004`，只发出该回答的浏览历史和收藏状态请求。

这将正文网络等待移出横滑路径，同时避免优化前一次挂载多个相邻富文本页面的 View 压力。

## 帧数据备注

一次回答打开窗口内共记录 476 帧：Android 新口径 deadline-missed 1 帧（0.21%），旧口径 jank 26 帧（5.46%），GPU P95 为 4 ms。GPU 开销较轻；现有证据更指向网络等待、JS/UI 线程工作和大量 View 挂载，而不是 GPU 绘制能力。

这份 Debug 基线已经促成正文缓存复用与相邻预取优化，但不能回答公式排版、Android 文本装饰和真正超长正文的问题。后续对照矩阵与替换路线见 [Renderer V2 迁移计划](./renderer-v2-plan.md)。
